Monitoring Pakai Bash

31 Januari, 2026 · 3 menit

Aku pengen tahu kalau CPU, RAM, atau disk di server Linux mulai kepenuhan, tanpa harus ngurus sistem monitoring yang ribet.

Prometheus dan Zabbix, misalnya, biasanya butuh agent di tiap server dan satu server pusat buat nampung datanya. Semua itu harus dipasang, diperbarui, dan dijaga tetap hidup.

Padahal bahannya sudah ada di server. Bash terpasang di hampir semua distro server, kecuali yang minimal kayak Alpine, dan angka yang kubutuhkan tinggal dibaca lewat free, df, ps, dan /proc/stat.

Jadi aku bikin effective-couscous, satu script Bash yang mengecek CPU, RAM, dan disk, lalu mengirim alert ke Telegram kalau ada yang melewati batas.

Pasangnya cukup clone repo dan siapkan config: 

git clone https://github.com/baguswjksn/effective-couscous.git
cd effective-couscous
mv conf.example .conf
chmod +x script.sh

Semua pengaturan ada di .conf, file Bash biasa yang dibaca pakai source. Isinya token bot Telegram, chat ID penerima, dan batas buat tiap metrik: 

BOT_TOKEN="token-bot"
TELEGRAM_USERS=("chat-id")

CPU_MAJOR=85
CPU_CRITICAL=90

MEM_MAJOR=85
MEM_CRITICAL=95

DISK_RULES=(
  "/:85:90:critical"
  "/var:70:85:critical"
  "/home:70:85:major"
)

Tiap mount point punya aturan sendiri dengan format MOUNT:MAJOR:CRITICAL:LABEL. LABEL itu tingkat keparahan saat batas pertama terlewati, jadi / bisa langsung dianggap critical di 85%, sementara /home baru major di 70%.

Kalau /var dan /home masih satu disk dengan /, hapus aja aturannya biar alert-nya nggak dobel.

Terakhir, daftarkan ke cron. Contoh ini jalan tiap lima menit, tinggal sesuaikan path-nya: 

*/5 * * * * cd /opt/effective-couscous && ./script.sh

Harus cd dulu, karena script-nya mencari .conf di folder tempat dia dijalankan.

Script ini agentless: nggak ada daemon yang harus dipasang dan dijaga tetap hidup, nggak ada port yang dibuka, dan nggak ada server pusat.

Cron menjalankan script-nya, script-nya mengecek, lalu selesai. Di antara dua jadwal nggak ada proses monitoring yang jalan dan makan RAM. Menghapusnya pun cukup buang baris cron dan foldernya.

Tiap jalan, RAM dihitung dari free, CPU dari /proc/stat, dan disk dari df. Kalau CPU atau RAM melewati batas, ps mengambil proses yang paling boros biar penyebabnya langsung kelihatan.

Pesannya dikirim ke API Telegram pakai curl, satu-satunya tool di sini yang kadang belum terpasang. Bisa ke beberapa orang sekaligus, tinggal tambah chat ID. Hasilnya kayak gini: 

critical(2026-01-20 04:00:38)(hostname ip)
Physical memory usage is now 23%, Top Processes
(python3(29932)-(3.10%);multipathd(3587)-(2.70%);snapd(992)-(1.50%))

critical(2026-01-20 04:00:38)(hostname ip)
Disk free on / is now 95%, out of total size 58G

RAM 23% dianggap critical karena waktu itu batasnya kuturunkan buat ngetes. Kalau mau ngetes tanpa mengirim apa-apa, ganti MODE di .conf jadi debug, dan semua angkanya bakal tampil di terminal.

Cara ini tentu ada batasnya. Script-nya jalan di server yang dipantau, jadi kalau server-nya mati, alert-nya ikut mati. Buat tahu server masih hidup atau nggak, tetap butuh pengecekan dari luar.

Script-nya juga nggak punya ingatan. Nggak ada riwayat atau grafik, dan selama angkanya masih di atas batas, alert yang sama terkirim lagi di tiap jadwal cron.

Angka CPU-nya juga belum pas. /proc/stat cuma dibaca sekali, jadi hasilnya rata-rata sejak boot, bukan beban saat ini. Makin lama server-nya hidup, makin kecil pengaruh lonjakan, jadi beban tinggi yang sebentar bisa nggak kedeteksi.

Kalau butuh grafik dan riwayat, pakai stack monitoring beneran. Kalau cuma pengen dikabari saat server mulai kepenuhan, satu script ini sudah cukup.

Kodenya ada di GitHub, sekitar 160 baris, jadi gampang dibaca dan diubah sendiri.
